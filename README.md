# Temperature Automation LAB

Независимый стенд для работы с физическим температурным контуром через Modbus RTU/TCP. По умолчанию приложение запускается в `HARDWARE`; пока контроллер, линия и карта регистров не настроены, каналы показывают `НЕТ СВЯЗИ`, а не синтетические температуры. Симуляционный API оставлен для разработческих проверок, но не предлагается оператору в интерфейсе.

## Запуск на Windows

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python main.py
```

Откройте http://127.0.0.1:8000. История хранится в `data/history.sqlite3`, выгружается кнопкой CSV. Тесты стандартной библиотеки: `python -m unittest discover -s tests`.

## Подключение оборудования

В этой среде обнаружен USB–RS-485 адаптер CH340 на `COM2`. Это подтверждает наличие последовательного адаптера, но не идентифицирует подключённый контроллер и не подтверждает его карту регистров. Автоматическое сканирование регистров и запись в неизвестное устройство не выполняются.

В диалоге оборудования задайте выбранный контроллер/модуль, транспорт Modbus RTU или TCP, параметры линии, Slave ID и три адреса регистров температуры из документации производителя. До явного разрешения выходов приложение работает только на чтение. Для разрешения записи дополнительно задайте адреса обеих выходных катушек по карте производителя и введите `ENABLE OUTPUT WRITES`; запуск HARDWARE требует отдельного подтверждения оператора. Неверная карта регистров, тип данных, порядок байтов или коэффициент масштабирования могут привести к неверным измерениям. Проверяйте настройки сначала на стенде/контроллере без подключённой силовой нагрузки.

Компьютерный GPIO не используется для управления нагрузкой. Нагреватель и вентилятор должны коммутироваться подходящим контроллером/силовым интерфейсом. Аппаратный аварийный останов, независимый ограничитель температуры, защита от перегрева и межблокировки должны быть реализованы в сертифицированной для применения аппаратной цепи и программе ПЛК. Программная команда останова и Modbus-связь не являются функцией безопасности; при потере связи ПО не может гарантировать отключение полевого выхода.

## Требуемые датчиковые интерфейсы

- PT100/PT1000: совместимый RTD-входной модуль или передатчик; прямое подключение к ПК не предполагается.
- Термопара: входной модуль нужного типа с компенсацией холодного спая либо подходящий преобразователь.
- 0–10 В / 4–20 мА: совместимый аналоговый вход или изолированный преобразователь; масштабирование определяется документацией модуля.
- Modbus RTU: контроллер/измерительный модуль с документированной картой регистров и адаптером RS-485.
- Modbus TCP: Ethernet-контроллер/шлюз с документированными адресами и типами регистров.
- USB: устройство с доступным API или драйвером; одного наличия USB-порта недостаточно.

В аппаратном режиме обрыв датчика определяется только по достоверному статусу канала/диагностическому флагу модуля. Значение вне настроенного диапазона само по себе не трактуется как доказательство обрыва.

## Состав

`frontend/` — веб-панель; `backend/app.py` — REST/WebSocket API; `backend/device_drivers/` — общий интерфейс и Modbus; `backend/signal_processing.py` — декодирование и масштабирование; `backend/pid_controller.py` — PID и блокировка; `backend/alarm_manager.py` — события и аварии; `backend/historian.py` — SQLite/CSV; `backend/configuration.py` — настройки; `tests/` — unit-тесты.
